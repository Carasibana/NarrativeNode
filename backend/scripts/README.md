# NarrativeNode MCP stdio wrapper — Phase 2.14

Tiny Python process that MCP host apps (Claude Desktop, Claude Code,
etc.) spawn via stdio. Boots clean regardless of whether
NarrativeNode is running, so the host stops reporting `narrativenode`
as unhealthy at boot when NN happens to be offline.

## Files

| File | What it is |
|---|---|
| `mcp_stdio_launcher.py` | The wrapper. Started by the host over stdio. |
| `mcp_catalogue.json` | Tool catalogue served at handshake. Auto-regenerated by NarrativeNode every time the MCP listener starts (gated on `mcp_auto_start` preference OR the user toggling MCP on). Committed to the repo so first-time users have a working catalogue before they've launched NN. |
| `test_mcp_stdio_launcher_smoke.py` | End-to-end smoke test. Runs the wrapper as a subprocess, sends `initialize` / `tools/list` / `tools/call`, validates offline-upstream behavior. Run via `.venv\Scripts\python.exe backend\scripts\test_mcp_stdio_launcher_smoke.py`. |
| `test_mcp_server_smoke.py` | (Pre-2.14) smoke test for the in-process FastMCP server — requires NN to be running. |
| `test_mcp_bridge_smoke.py` | (Pre-2.14) smoke test for the WebSocket bridge. |

## How it behaves

- **Host launches wrapper at boot** → wrapper reads the catalogue
  file and responds to `initialize` / `tools/list` immediately.
  Host marks `narrativenode` as healthy.
- **AI calls a tool, NarrativeNode running** → wrapper opens a fresh
  `streamablehttp_client` to `http://127.0.0.1:13316/mcp/server/`,
  forwards `tools/call`, returns the upstream's result verbatim.
  ~50-100 ms per call.
- **AI calls a tool, NarrativeNode NOT running** → wrapper catches
  the connection failure and returns a regular tool-result
  envelope with the text "NarrativeNode isn't running. Launch it
  and retry the call." rather than crashing or returning an MCP
  error. Hosts render this in the chat surface so the user knows
  what to do.

## Catalogue lifecycle

- Lives at `backend/scripts/mcp_catalogue.json`.
- Regenerated by `_ensure_catalogue_current()` in
  `backend/services/mcp_control.py` whenever
  `McpStaticListener.start()` fires.
- Skip-path (no source change): ~1 ms.
- Regen path: walks `await mcp.list_tools()`, writes atomically
  (`.tmp` + `os.replace`), stamps a SHA-1 fingerprint over
  `mcp_server.py` + every `.py` in `backend/models/`.
- If the source fingerprint matches the stamp in the existing
  file, nothing happens.

If a module *outside* `mcp_server.py` + `backend/models/` ever
affects tool schemas (we don't expect this but it's theoretically
possible), the catalogue can go stale. Delete
`mcp_catalogue.json` to force a one-time regen on the next MCP
listener start.

## Host configuration

**`<NN_ROOT>` in every snippet below is a placeholder. Replace it
with the absolute path to your NarrativeNode repo on disk before
pasting** — the literal placeholder text won't resolve to anything
and the host will fail to launch the wrapper. Host configs require
absolute paths because the host's working directory isn't
predictable at launch time. **Use forward slashes everywhere**,
including on Windows; both JSON configs and the Claude Code CLI
handle them fine.

### Claude Desktop

Edit `%APPDATA%\Claude\claude_desktop_config.json` (Windows) or
`~/Library/Application Support/Claude/claude_desktop_config.json` (macOS)
and add a `narrativenode` entry under `mcpServers`:

```json
{
  "mcpServers": {
    "narrativenode": {
      "command": "<NN_ROOT>/.venv/Scripts/python.exe",
      "args": ["<NN_ROOT>/backend/scripts/mcp_stdio_launcher.py"]
    }
  }
}
```

On macOS / Linux the venv Python is at
`<NN_ROOT>/.venv/bin/python` instead.

**Use the venv Python explicitly** — the wrapper depends on the
`mcp` package installed in NN's venv. A system Python without
that package will fail at import.

Restart Claude Desktop. The `narrativenode` server should be
healthy at boot regardless of whether NarrativeNode is running.

### Claude Code

```sh
claude mcp add narrativenode \
  <NN_ROOT>/.venv/Scripts/python.exe \
  <NN_ROOT>/backend/scripts/mcp_stdio_launcher.py
```

On macOS / Linux the venv Python is at `<NN_ROOT>/.venv/bin/python`.

Verify:
```sh
claude mcp list
```
Should show `narrativenode: ... - ✓ Connected` regardless of whether
NarrativeNode is running.

### Override the upstream URL

If NarrativeNode is reachable at a different URL (e.g. a dev port
override), set `NN_MCP_URL` in the host's environment block:

```json
{
  "mcpServers": {
    "narrativenode": {
      "command": "...",
      "args": ["..."],
      "env": { "NN_MCP_URL": "http://127.0.0.1:8001/mcp/server/" }
    }
  }
}
```

Default is `http://127.0.0.1:13316/mcp/server/` (the static A1Z26 port).

## Smoke testing

```sh
cd backend
.venv\Scripts\python.exe scripts\test_mcp_stdio_launcher_smoke.py
```

Runs the wrapper as a subprocess with `NN_MCP_URL` overridden to a
known-unreachable port, exercises `initialize` / `tools/list` /
`tools/call`, asserts the offline-call path returns the friendly
envelope. Doesn't require NarrativeNode to be running.

## Inherited limitations

The wrapper sidesteps the boot-time handshake failure but inherits
exposure to other known Claude-side bugs:

- [#13646](https://github.com/anthropics/claude-code/issues/13646) — Claude Code doesn't refresh `tools/list` on `notifications/tools/list_changed`. We don't currently emit this notification so it's a non-issue here.
- [#31893](https://github.com/anthropics/claude-code/issues/31893) — broader gaps in Claude Code's MCP handling (`list_changed`, progress, sampling, async).
- [#61052](https://github.com/anthropics/claude-code/issues/61052) — Claude Desktop silently disconnects remote MCP children. Affects `mcp-remote` specifically; our stdio child wrapper isn't a remote child but disconnection-without-relaunch could still bite.

If any of these become user-visible, the workaround is to restart
the host app. The wrapper doesn't try to paper over Claude bugs
beyond the boot-time one.
